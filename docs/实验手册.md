# 后端实验手册：命令、观察、失败路径

配套：[主手册](后端学习手册.md) · [面试问答](面试问答与进阶练习.md) · [验收记录](改造与验收.md)

所有命令在项目根目录执行。默认端口 8080；当前验收用 18080，以下统一使用 18080。示例密码只适用于本地演示。不要在生产数据库进行学习实验。

## 实验 0：确认环境与启动链路

目标：分清编译通过、依赖启动、HTTP 可用、业务正常四种状态。

~~~powershell
java -version
docker version
docker compose up -d
docker compose ps
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run "-Dspring-boot.run.arguments=--server.port=18080"
~~~

另开终端：

~~~powershell
Invoke-RestMethod http://localhost:18080/actuator/health
~~~

预期 status 为 UP，浏览器打开服务地址显示登录页。MySQL 是 3306；Redis 是 6379；RabbitMQ 协议端口 5672、管理页 15672。不要把 MQ 管理端口当成 Java 应用端口。

| 错误 | 优先检查 |
|---|---|
| docker daemon unavailable | Docker Desktop 是否启动 |
| Docker Access denied | 当前进程访问引擎的权限 |
| Connection refused | 容器、地址、端口 |
| Address already in use | 应用端口占用 |
| Flyway checksum mismatch | 是否修改了已经执行的迁移 |
| table/column missing | V2 是否执行、是否连错库 |
| Maven 下载失败 | 网络和依赖仓库 |
| 编译 API 不存在 | 示例与当前依赖版本是否对应 |

不要用清库解决所有启动问题。先记录完整错误，再找到发生错误的层。

## 实验 1：建立会话并理解认证

~~~powershell
$baseUrl = 'http://localhost:18080'
$citizenLogin = Invoke-RestMethod "$baseUrl/api/auth/login" -Method Post -ContentType 'application/json' -Body '{"username":"citizen","password":"User@123"}'
$citizenHeaders = @{ Authorization = "Bearer $($citizenLogin.data.accessToken)" }
$adminLogin = Invoke-RestMethod "$baseUrl/api/auth/login" -Method Post -ContentType 'application/json' -Body '{"username":"admin","password":"Admin@123"}'
$adminHeaders = @{ Authorization = "Bearer $($adminLogin.data.accessToken)" }
~~~

不要公开完整 Token。错误密码预期 401；无 Token 查询记录也预期 401。401 和 403 不同，前者没有有效身份，后者身份已知但权限不足。

练习：解码 JWT 的 payload，解释为什么内容可读仍能防篡改。答案必须包含签名，不能说 Base64 是加密。

## 实验 2：创建记录和幂等回放

~~~powershell
$submitKey = 'study-' + [Guid]::NewGuid().ToString()
$createHeaders = @{ Authorization = $citizenHeaders.Authorization; 'Idempotency-Key' = $submitKey }
$createBody = '{"district":"象山区","category":"WATER","quantity":1,"priority":"NORMAL"}'
$created = Invoke-RestMethod "$baseUrl/api/relief-requests" -Method Post -Headers $createHeaders -ContentType 'application/json' -Body $createBody
$requestNo = $created.data.requestNo
$created.data
~~~

预期包含 requestNo、PENDING、非空 createdAt。原样重试：

~~~powershell
$replayed = Invoke-RestMethod "$baseUrl/api/relief-requests" -Method Post -Headers $createHeaders -ContentType 'application/json' -Body $createBody
$replayed.data.requestNo -eq $requestNo
~~~

预期 True。保持相同 key，但把 quantity 改为 2，预期 409。换 key 才表达一张新的业务请求。

数据库核对：

~~~sql
SELECT request_no, requester_id, idempotency_key, quantity, status
FROM relief_request
WHERE idempotency_key = '替换为实验中的key';
~~~

同用户同键只有一条；另一个用户使用相同 key 可以拥有独立记录。用普通“先查有没有”不能替代数据库唯一约束，因为并发时两次检查都可能读到不存在。

思考：网络超时后换一个新 key，会不会造成重复？会。因此客户端重试必须遵守幂等契约，而不只是后端部署 Redis。

## 实验 3：归属权限和跨设备查询

~~~powershell
Invoke-RestMethod "$baseUrl/api/relief-requests?page=0&size=20" -Headers $citizenHeaders
Invoke-RestMethod "$baseUrl/api/relief-requests?page=0&size=20&status=PENDING" -Headers $citizenHeaders
Invoke-RestMethod "$baseUrl/api/relief-requests?keyword=$requestNo" -Headers $citizenHeaders
~~~

换一个浏览器登录同一居民，仍能看到记录。现在列表来自 MySQL，不再依赖旧本机缓存。

用管理员创建一张管理员自己的请求，再用居民 Token 查询它，预期 404。用管理员 Token 查居民请求，预期 200。列表没有开放 requesterId 参数供居民选择其他用户。

反向断言：

- 居民列表不应出现管理员创建的请求。
- 放大 size 不能绕过归属条件。
- keyword 精确匹配他人编号仍应返回空列表。
- 删除浏览器缓存不应删除数据库记录。
- 未登录访问不能成功。
- 详情与列表必须使用一致的可见性规则。

## 实验 4：一键真实接口验证

~~~powershell
node tests/api-smoke.mjs
~~~

需要 Node.js 和运行中的服务。脚本会新增两张小请求，不删除已有数据；其中一张居民饮用水请求预留 1 份库存。输出会给出编号。

覆盖 14 类场景：双角色登录、无 Token 拒绝、创建时间、幂等回放、正文冲突、用户幂等作用域、详情越权、分配越权、负页码、错误枚举、服务端筛选、四请求并发分配、分配后状态、分配后幂等回放。

关键断言：4 个并发分配请求中恰好 1 个成功，3 个返回 409。它验证当前真实数据库下同一请求的并发保护，不是任意规模吞吐性能证明，也不是所有故障恢复的穷举。

若报无库存，检查辖区、类别、有效期、可用量。不要为了测试通过删除已有业务数据。每次重跑会产生新的两张请求与 1 份水预留。

## 实验 5：用两个 MySQL 会话观察锁

分别开两个终端：

~~~powershell
docker compose exec mysql mysql -uapp -p resilience_hub
~~~

在提示中输入数据库演示密码。选择一个真实 requestNo。会话 A：

~~~sql
START TRANSACTION;
SELECT id, request_no, status
FROM relief_request
WHERE request_no = '替换编号'
FOR UPDATE;
~~~

保持事务打开，会话 B 执行相同 SQL。预期 B 等待。A 执行 ROLLBACK，B 获得锁后也执行 ROLLBACK。本实验只做锁定读，不改变记录。

需要解释：

1. 普通 SELECT 与 FOR UPDATE 为什么不同。
2. 查询执行完成为什么锁仍保留。
3. 事务内在调试器断点暂停为什么影响其他用户。
4. 为什么数据库锁定读比本机 synchronized 更适合多实例协调。
5. 为什么长事务影响吞吐。

进阶死锁实验只在独立测试库做：两事务以相反顺序锁两行，观察死锁错误与回滚。不要在共享环境中无限持锁。

## 实验 6：观察 FEFO、预留量和分配明细

~~~sql
SELECT l.id, s.name, s.district, l.category,
       l.quantity, l.reserved_quantity,
       l.quantity - l.reserved_quantity AS available,
       l.expires_at
FROM supply_lot l
JOIN shelter s ON s.id = l.shelter_id
ORDER BY s.district, l.category,
         CASE WHEN l.expires_at IS NULL THEN 1 ELSE 0 END,
         l.expires_at, l.id;
~~~

分配后查：

~~~sql
SELECT r.request_no, a.supply_lot_id, a.quantity, a.status
FROM allocation a
JOIN relief_request r ON r.id = a.request_id
WHERE r.request_no = '替换编号'
ORDER BY a.id;
~~~

同一请求可以对应多个批次，但同请求同批次不应出现重复明细。总量未减少、预留量增加，意味着尚未完成实物发放。

独立测试库练习：建立两个不同有效期的同类批次，再加一个无有效期批次，让请求跨批次分配，断言无有效期批次排在最后。先设计固定数据，再断言固定结果，不依赖会随着时间过期的演示数据。

## 实验 7：读懂执行计划

~~~sql
SHOW INDEX FROM relief_request;

EXPLAIN
SELECT request_no, status, created_at
FROM relief_request
WHERE requester_id = 2
ORDER BY created_at DESC, id DESC
LIMIT 20;

EXPLAIN
SELECT request_no, status, created_at
FROM relief_request
WHERE requester_id = 2 AND request_no LIKE '%123%'
ORDER BY created_at DESC, id DESC
LIMIT 20;

EXPLAIN
SELECT id, request_no FROM relief_request
ORDER BY created_at DESC, id DESC
LIMIT 10000, 20;
~~~

用户 ID 按实际数据修改。观察 key、rows、Extra。小表走全表扫描不一定坏，大表用了索引也不一定快。

实验报告要记录：数据量、索引定义、SQL、执行计划、耗时、返回行数。对比不同数据量和命中率，不要只提交“用了索引”的截图。

思考：包含匹配能否高效定位 B+Tree？深分页为何需要扫描被跳过部分？如何使用 createdAt 和 id 做游标？

## 实验 8：查看 Redis 缓存、租约与 TTL

~~~powershell
docker compose exec redis redis-cli --scan --pattern 'shelters:district:*'
docker compose exec redis redis-cli --scan --pattern 'idem:*'
docker compose exec redis redis-cli --scan --pattern 'rate:*'
~~~

用 SCAN，不对大 keyspace 执行 KEYS。复制一个实际 key：

~~~powershell
docker compose exec redis redis-cli TTL '替换为实际key'
docker compose exec redis redis-cli GET '替换为实际key'
~~~

访问站点 API 后观察缓存。过期时间应在几分钟量级。缓存里的 Base64 不是加密。

幂等 DONE 值含资源编号，长期业务约束在 MySQL。可以只删除本次实验精确匹配的幂等缓存 key，再用原键重试，仍应返回原请求。不要使用 FLUSHALL 或通配删除，这会影响限流、缓存和消费去重。

回答：TTL 抖动缓解雪崩的哪一种原因？Redis 整体宕机时还需要什么？为什么空值缓存不能阻止无限枚举不同空 key？

## 实验 9：跟踪 Outbox 和消息确认

~~~sql
SELECT id, aggregate_id, event_type, status, retry_count,
       next_retry_at, published_at
FROM outbox_event
ORDER BY id DESC
LIMIT 20;
~~~

分配之后 PENDING 事件正常应变为 PUBLISHED。RabbitMQ 管理页查看 resilience.events 与 allocation.notification。队列为空可能是消费者已经取走，不能据此判断消息没发。

Java 日志中的模拟通知表示消费者执行，不表示真实短信送达。

受控故障实验：只在自己的独立开发环境、确认无人依赖时停止 RabbitMQ：

~~~powershell
docker compose stop rabbitmq
~~~

提交并分配小请求，观察 Outbox 重试而不是错误标记已发布。恢复：

~~~powershell
docker compose start rabbitmq
~~~

等 next_retry_at 到期后检查重投递。达到 10 次失败进入 FAILED，不会无限自动重试，当前没有管理界面手工补发功能。

本轮并未执行停 MQ 故障注入；这是提供给学习者的实验，不是已经通过的验收证据。

## 实验 11：单元测试与故意破坏实验

~~~powershell
.\mvnw.cmd test
node --test tests/frontend.test.cjs
~~~

Mockito 测试验证业务分支，不证明真实数据库锁。Node 测试使用隔离上下文验证前端逻辑，也不代替浏览器布局检查。

在独立分支中临时移除 getVisible 的归属判断，测试必须变红。恢复之后变绿。这叫验证测试真的会发现问题，而不是“运行了一个永远成功的断言”。

相同方法测试幂等正文比较、分配状态检查、前端响应版本保护。不要把故意破坏的版本部署给其他人。

## 实验 12：界面完整验收

1. 居民登录，新建 1 份饮用水请求。
2. 打开详情，记录编号和时间。
3. 退出，工作人员登录。
4. 搜索该编号，打开分配弹窗，核对后确认。
5. 居民重新登录，看到已分配状态。
6. 在另一浏览器登录，确认跨设备可见。
7. 按状态筛选，清空筛选，翻页。
8. 切换共享站辖区，观察查询时间。
9. 缩窄窗口，检查表格区域内滚动与弹窗。
10. 断开服务时确认显示失败，而不是“没有记录”。

此流程会改变演示库存，使用小数量。当前没有取消/退回，不能假装点错之后系统会自动归还库存。

## 实验 13：性能实验怎么设计

先固定数据量、用户比例、读写比例与测试时长。例如 90% 查询、10% 新建，与 100% 热点库存分配是完全不同的负载。

记录吞吐、错误率、P50/P95/P99、数据库连接等待、慢 SQL、GC 暂停。同步记录 CPU、内存和数据库锁。吞吐增加但错误率升高不是优化成功。

逐步增加并发，不直接打满开发电脑；停止条件可以是错误率超过约定阈值、数据库排队持续上涨。性能阈值需要自己制定，不把本文的演示参数当成生产 SLA。

学习目标：能指出瓶颈是 CPU、I/O、连接池还是热点锁。不要只给出“线程数太少”的猜测。

## 实验 14：故障记录模板

~~~text
现象：接口、输入、角色、时间
预期：HTTP 状态与业务状态
实际：code、Trace ID、日志片段
范围：所有用户或一个用户；所有记录或一条记录
假设：按可能性列出至少两种
验证：对应的只读检查
修复：改变了哪个保证边界
回归：成功、失败、并发路径
限制：仍未验证的故障窗口
~~~

面试时“怎么确认修复有效”应回答具体测试和观测，而不是“我觉得这样更安全”。

## 实验 15：停机与恢复

停止 Java 用运行终端 Ctrl+C。停止依赖：

~~~powershell
docker compose stop
~~~

移除容器但保留已定义的 MySQL 卷：

~~~powershell
docker compose down
~~~

不要添加 -v，除非明确需要删除卷。Redis 和 RabbitMQ 当前未配置专用命名数据卷，删除并重建的效果不同于 stop/start；这属于生产化待补项。

重启后检查迁移历史、求助记录和健康状态。恢复能力最终要通过备份恢复演练验证，不能只看容器重新变绿。
