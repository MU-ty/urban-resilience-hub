## 1. 先理解项目为什么存在

### 1.1 业务并不是“换皮商城”

居民遇到物资短缺时提交求助：辖区、物资类别、数量、紧急程度。工作人员查看请求后执行分配。系统查找同辖区的库存批次，优先预留即将到期的有效物资，并产生一个“已分配”的通知事件。

这里的“分配”是**库存预留**，不是居民已经领取。SupplyLot 中的 reservedQuantity 增加，quantity 总量没有减少。当前没有实物发放、签收、取消、退回、库存入库和补分配完整流程。学习时要区分“程序已经做的事”和“业务最终想做的事”。

系统的不变量：

- 任何批次的预留量不能超过库存量。
- 同一居民同一幂等键不能创建两张求助单。
- 居民只能读取自己的求助记录，工作人员可以读取全部记录。
- 一次分配涉及的库存预留、分配明细、求助状态和 Outbox 事件必须同成同败。
- 页面显示服务端实际查询结果；没有结果与请求失败是不同状态。

把这些条件写在纸上，比先背注解名称更重要。评估设计时，先问“这条不变量靠哪一层保证”。

### 1.2 为什么采用模块化单体

所有 Java 模块在一个进程里，MySQL、Redis、RabbitMQ 是独立服务。单体不等于杂乱：Controller、Service、Repository 的边界仍然清晰。优点是启动简单，库存事务可以留在一个数据库里，排错时能追踪完整调用栈。

如果拆成多个服务，网络超时、部分失败、接口版本、调用链和运维负担会立即增加。当前可以学习分布式问题，但没有必要为了显示“高级”先把单次数据库事务拆散。

### 1.3 学习不是记住结论

每个主题按四个问题学习：

1. 它解决了什么具体问题？
2. 没有它会怎样失败？
3. 当前代码把保证放在哪里？
4. 在什么条件下，这个保证失效？

例如“Redis 单线程”不是缓存一致性的证明，“加了事务”不是跨数据库和 MQ 原子性的证明，“使用 JWT”不是接口无漏洞的证明。

## 3. 一次 HTTP 请求如何穿过系统

以 POST /api/relief-requests 为例：

~~~text
浏览器提交 JSON、Bearer Token、Idempotency-Key
  → Servlet 容器接收 HTTP 请求
  → 请求追踪过滤器设置 Trace ID
  → Spring Security 验证 Token、建立身份
  → Redis 固定窗口限流
  → Spring MVC 定位 Controller
  → JSON 反序列化为 CreateCommand
  → Bean Validation 检查参数
  → Controller 查询是否可以回放旧结果
  → Redis 获取短租约
  → Service 事务写入 MySQL
  → 数据库唯一约束兜底
  → Redis 标记完成
  → Controller 映射 RequestView
  → JSON 返回浏览器
~~~

这里既有 Servlet 容器过滤器，也有 Security 过滤器链。不要凭文件顺序猜执行顺序；要看注册方式及 addFilterBefore/addFilterAfter。TraceIdFilter 的实际容器顺序也应以启动配置验证，不把它假定为所有错误请求都一定最先执行。

### 3.1 HTTP 状态码和业务 code 各负责什么

HTTP 状态码表达大类：请求参数错、未认证、权限不足、数据冲突、服务器出错。JSON 中的 code 表达更精确的业务原因。不要所有接口都返回 HTTP 200，再靠 message 判断失败。

本项目常用约定：

| 状态码 | 意义 | 示例 |
|---|---|---|
| 200 | 操作成功 | 查询成功、创建成功、幂等回放 |
| 400 | 请求形状或参数非法 | 错误枚举、缺请求头、负页码 |
| 401 | 未登录或认证失败 | 无 Token、过期 Token、密码错误 |
| 403 | 已认证但无操作权限 | 居民尝试分配 |
| 404 | 目标不可见或不存在 | 查询他人求助时也返回 404 |
| 409 | 业务冲突 | 已分配、幂等键对应不同内容 |
| 429 | 触发频率限制 | 同 IP 一分钟请求超额 |
| 500 | 未预料的服务端错误 | 数据库或基础设施异常未分类处理 |

创建目前返回 200 是本项目约定；新 API 也可设计为 201 并带 Location。接口规范的一致性比机械背诵一个数字更重要。

### 3.2 Trace ID 为什么有用

发生 500 时，用户只应看到可理解的通用提示，服务日志需要记录完整异常。Trace ID 让前端响应和后端日志能够对上。本项目只允许 1～64 位字母、数字、下划线和连字符的外部 Trace ID，其他值重新生成，避免任意长字符串污染日志。

MDC 是线程上下文机制，不是分布式追踪系统。跨异步任务、MQ、服务之间的关联还需要明确传播，当前没有完整的 OpenTelemetry 链路。

## 4. Java 基础：对象、类型、异常与不可变性

### 4.1 Entity、DTO、Command 为什么分开

ReliefRequest 是数据库实体，带有主键、状态、创建人和版本号。CreateCommand 只包含用户被允许填写的内容；RequestView 只包含允许对外公开的数据。

如果直接让用户提交 Entity，就可能收到伪造的 requesterId、status、version，造成批量赋值漏洞。客户端不应决定“这是谁的记录”，创建人必须从已经认证的 Authentication 推导。

record 很适合 DTO：结构简洁，字段引用不能重新赋值，会自动生成访问器和 equals/hashCode。但 record 不是深度不可变：如果一个字段是可变 List，列表内部仍可变。需要 List.copyOf 等防御性复制。

### 4.2 基本类型与包装类型

int 无法表达 null，Integer 可以。请求字段是否允许省略，会影响 DTO 的选择。CreateCommand.quantity 是 int，缺字段可能按 0 处理，然后由 @Min(1) 拒绝。若想返回“必须填写数量”，可以改 Integer 配合 @NotNull、@Min，并测试 JSON null 与缺字段两种情况。

金额不要用 double；它是二进制浮点，很多十进制小数不能精确表示。若未来加入采购金额，应使用 BigDecimal，明确 scale、舍入规则和数据库 DECIMAL，而不是靠格式化隐藏误差。

### 4.3 equals 和 hashCode

equals 相等的对象必须具有相同 hashCode；相同 hashCode 不代表 equals 相等。用作 HashMap key 的对象，其参与 hashCode 的字段不应在入表后改变，否则可能“对象还在 Map 里，却查不到”。

JPA Entity 的相等性更复杂：ID 可能在持久化前为 null，还存在代理对象。不要随意给 Entity 自动生成“包含所有字段”的 equals/hashCode，尤其不能把懒加载关联全部纳入。

### 4.4 异常为什么要分类

业务异常是预期失败，如“无可用库存”。系统异常是预期之外的失败，如连接断开。前者应给明确状态和可操作提示，后者应记录异常堆栈。

try-with-resources 不仅用于文件，本项目的 Redis Lease 也实现 AutoCloseable：正常提交后保留完成标记，异常退出时释放自己的租约。需要注意 close 本身也可能失败；资源释放不是“绝不会抛异常”。

Checked Exception 与 RuntimeException 的区别不仅是要不要写 throws，还会影响默认事务回滚规则。不要为了少写 try/catch 把所有异常吞掉；否则业务已经部分失败，事务却以“成功返回”结束。

## 5. 集合、泛型、Stream：写业务代码必须懂的部分

### 5.1 ArrayList、LinkedList 与 HashMap

ArrayList 使用数组，按下标访问快，尾部追加摊销开销小。中间插入删除会移动元素。LinkedList 有节点对象和指针成本；“链表插入 O(1)”要求已经定位节点，按索引查找仍要遍历。

HashMap 平均查找复杂度近似 O(1)，但具体性能取决于哈希分布、容量和碰撞。它不是线程安全容器。多线程共享修改 HashMap 不能只靠“写得很少”保证正确。

在项目中：分配结果用 ArrayList 顺序收集；缓存解码返回列表；前端利用 Map 合并记录的做法是 Java HashMap 的同类思想。选择容器先看访问模式，不要只背结构。

### 5.2 泛型与类型擦除

JpaRepository<ReliefRequest, Long> 表达实体类型与 ID 类型，编译期防止把 Shelter 当作 ReliefRequest 保存。多数 Java 泛型类型信息在运行时被擦除，因此不能直接 new T()，反序列化 List<T> 时也需要额外类型信息。

“泛型擦除”不代表类文件里完全没有泛型信息；声明中的签名可以供反射读取。但运行时的普通对象不会为每个 T 生成一份独立的 Java 类。

### 5.3 Stream 不是免费的性能优化

result.stream().map(...).toList() 适合把实体转换为 DTO。不要在 map 中隐藏数据库写入，不要在 parallelStream 中不加思考地发起数据库请求。并行流会引入线程、连接池争用和事务上下文传播问题。

Stream.toList() 的结果不能假定可修改；确实需要继续 append 时，明确复制到 ArrayList。Optional 适合表达“查询可能没有结果”，不应用 get() 把缺失条件推迟成不可读的异常。

练习：把 RequestView 映射分别用 for 循环和 Stream 写一遍，比较可读性，而不是凭语法短判断优劣。

## 6. JVM：内存、类加载与 GC

### 6.1 堆和栈怎么联系到接口

方法调用形成栈帧，保存局部变量、操作数栈等；对象一般存放在堆里，局部变量可以持有指向对象的引用。JIT 优化可能进行逃逸分析等处理，不能把每一个 new 机械地解释为“必须一次真实堆分配”。

一次查询返回几十万个 Entity，会扩大堆内对象数量；事务持久化上下文还可能持有这些对象，让它们不能及时回收。这也是分页限制最大 100 条的实际意义，不只是接口规范。

### 6.2 GC 解决什么，解决不了什么

GC 回收不可达对象，不能自动解决逻辑上的无界缓存。若静态 Map 一直保存旧数据，GC 认为它们仍然可达。ThreadLocal 没有清理，也可能让线程长期持有对象。

响应变慢不一定是 GC。可能是 SQL 变慢、连接池排队、数据库锁、CPU 饱和、DNS、MQ 确认等待。应先看耗时分布、线程状态和 GC 日志，避免一上来改垃圾回收器。

### 6.3 容器内存不能全部给堆

进程还有元空间、线程栈、直接内存、JIT 代码缓存等。Dockerfile 中 MaxRAMPercentage=75 表达一种预算，不是“75% 永远安全”。容器的实际内存限制、线程数量和直接内存都需要一起测量。

常见排障顺序：

1. 确认进程是否真的被 OOM Killer 杀死，还是 Java 抛 OutOfMemoryError。
2. 记录堆使用、GC 频率、暂停时间、活跃线程和请求量。
3. 检查大集合、缓存增长、批量导出和连接泄漏。
4. 在受控环境抓 heap dump，再找保留对象链。
5. 修复生命周期或容量问题，然后再讨论参数。

### 6.4 Java 21 与本机新 JDK

项目目标是 Java 21，但本机验证用 Java 25。调试虚拟线程、GC、反射、Unsafe 警告时，要分清版本差异。编译通过不等于已经在 Java 21 运行镜像中验证过所有行为。Docker 镜像运行验收是可补充的检查，本轮没有声称已完成。

## 7. 并发：从线程安全到资源限制

### 7.1 三个维度

原子性：操作不会被观察为中间状态。可见性：一个线程的写入如何被另一个线程看到。有序性：编译器和处理器允许哪些重排。

volatile 可以用于可见性和一定的有序性，但 count++ 仍是读、加、写三个步骤，不能靠 volatile 变成原子计数。AtomicInteger 适合单值原子更新；复合业务不变量通常需要锁或数据库事务。

### 7.2 synchronized 与 ReentrantLock

二者都能协调同一 JVM 内线程。ReentrantLock 提供可中断、超时尝试等灵活控制，但必须 finally 解锁。无论用哪个，都不能保护另一个 JVM 进程的库存写入。

本项目库存正确性放在 MySQL 锁和事务里，因为数据库是多个应用实例共享的事实来源。若用 synchronized 包住分配方法，单实例看似有效，一旦启动第二个实例就不够了。

### 7.3 CAS、ABA 与乐观锁

CAS 比较预期旧值，再写入新值。ABA 指值从 A 变为 B 再变回 A，比较值本身无法发现中间变化。带版本号的比较可以识别变化历史，但也要考虑版本更新的完整路径。

Entity 的 @Version 会让更新带版本条件；更新不到预期行数时提示冲突。当前分配还使用悲观锁，@Version 是另一层冲突检测，不代表应该无限自动重试所有业务。

### 7.4 线程池和背压

传统线程池的重要参数是核心线程数、最大线程数、队列长度、拒绝策略、超时和线程命名。无界队列可能把过载转成内存膨胀；过多线程可能转成频繁切换与下游连接争抢。

虚拟线程适合大量等待 I/O 的任务，不能增加数据库连接数，也不会把 CPU 密集计算变快。本项目 Hikari 最大连接数为 20：即使有很多虚拟线程，能同时持有数据库连接的事务仍受这一限制。虚拟线程的用法和约束应按目标 JDK 验证。[Java 21 官方说明](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html)

### 7.5 两层并发控制

应用层需要限制进入系统的请求量，数据库层需要保证数据正确。限流不是锁，锁不是限流。限流减少过载；数据库锁让被接受的请求按安全顺序修改共享数据。

学习时做两个实验：低并发下重复请求，检查幂等；高并发下不同请求竞争库存，检查库存不变量。它们不是同一个问题。

## 8. Spring：IoC、Bean 生命周期与 AOP

### 8.1 构造器注入的价值

Service 通过构造器接收 Repository，测试时可以直接传 mock，不依赖 Spring 上下文。final 字段表达依赖在构造之后不更换。必需依赖缺失时启动失败，比运行到某个接口才空指针更容易定位。

IoC 的核心不是“少写 new”，而是对象创建、依赖组装与生命周期交给容器统一管理。仍应避免把可变的每次请求状态存进单例 Service 字段。

### 8.2 单例 Bean 不等于线程安全

@Service 默认通常是单例，多请求会共享同一实例。当前 Service 字段主要是依赖引用，局部变量放在方法内，不保存“当前用户”“当前请求编号”到实例字段中。

如果把 currentRequestNo 设为 Service 字段，请求 A 刚赋值，请求 B 就可能覆盖。线程安全来自状态设计，不来自 Spring 注解。

### 8.3 AOP 和代理

审计、事务都属于横切能力。代理在业务方法前后插入逻辑。对外经过代理的调用能被拦截，同对象内部 this.method() 调用通常不会再次经过代理。

因此，“在 private 方法上加事务注解然后直接调用”不能作为新事务的保证。项目中的 service 内部辅助调用依赖外层已建立事务；若要独立事务，需要明确经过另一个 Bean 或使用 TransactionTemplate。此处代理边界以 Spring 官方说明为准。[事务注解说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

### 8.4 审计当前做到哪里

AuditAspect 在带 @Audited 的 Controller 成功返回后写审计。它只记录方法级信息，resourceId 当前未完整填充，失败请求不在该 after-returning 审计里。

特别要讨论：业务事务已经提交，审计写入却失败，调用方可能看到失败但业务已经成功。幂等回放能降低重复创建风险，但不意味着审计系统达到生产要求。更严格的设计可以把审计事件与业务同事务持久化，再异步落日志。

## 9. Spring MVC 与接口设计

### 9.1 Controller 要做什么

接收参数，触发校验，取得登录身份，调用业务服务，把结果映射为响应。库存分配循环不应该写在 Controller。Controller 也不应直接返回携带所有数据库字段的实体。

CreateCommand 使用 @NotBlank、@Size、@NotNull、@Min、@Max。HTTP 请求中的枚举不是“随便一个字符串”；无效值反序列化失败，当前映射为 400。

### 9.2 统一响应不代表捕获一切后返回成功

GlobalExceptionHandler 将不同异常映射到不同 HTTP 状态。兜底处理器必须日志记录异常，不应把堆栈和内部 SQL 直接给客户端。

过滤器链里的认证错误不一定进入 MVC Advice，因此 SecurityConfig 另设认证入口和拒绝处理器。这解释了为什么只写 @RestControllerAdvice 还不足以统一所有 401/403。

### 9.3 分页协议

GET /api/relief-requests 支持 page、size、keyword、status。page 从 0 开始，size 为 1～100，keyword 最长 40。排序固定为 createdAt DESC, id DESC，防止相同创建时间导致页内顺序不稳定。

响应采用自定义 PageView，避免直接序列化 Spring Data 内部 PageImpl 结构导致协议随版本变化：

~~~json
{
  "code": "OK",
  "message": "success",
  "data": {
    "content": [],
    "number": 0,
    "size": 20,
    "totalElements": 0,
    "totalPages": 0
  }
}
~~~

前端显示页码从 1 开始，调用后端仍传 0 开始的页码。这一偏移必须在界面层处理清楚。

### 9.4 筛选不是前端“藏起来”

后端根据身份自动加 requesterId 条件，居民不能通过传 userId 选择别人的记录。status 和 keyword 条件在数据库中执行，因此作用于全部数据，而不是只对当前页过滤。

keyword 使用 Criteria 参数化条件，并转义 LIKE 中的 %、_ 和转义符自身。SQL 参数化解决注入；转义 LIKE 通配符解决查询语义被输入意外扩大。这两个问题不同。

## 10. JPA、脏检查与数据库连接池

### 10.1 save、flush、commit

save 不等于事务已经提交；flush 把持久化上下文变化同步到数据库，也不等于 commit。只有事务提交成功，变化才最终对外成立。

本项目创建求助使用 saveAndFlush，便于尽早触发唯一键约束；随后事务仍可能回滚。Controller 之外的 service 事务代理返回时，正常情况下事务已经提交。

### 10.2 为什么分配代码没有每行都 save

事务内查询得到的 Entity 是受管理对象，修改 reservedQuantity 或 status 后，Hibernate 脏检查会在 flush 时生成更新 SQL。理解这一点才能判断“没有调用 save”是不是 bug。

但如果 Entity 已脱离上下文，直接修改不一定会持久化。不要把 JPA 的托管行为推广到任意 Java 对象。

### 10.3 数据库生成的时间

created_at 由 MySQL 默认值生成。以前对象保存后内存字段可能仍为 null。现在 Request 的 createdAt 使用 Hibernate 生成值标记，创建响应就能得到真实时间。数据库生成值与 Java 内存状态的同步需要显式考虑。

时间以 Instant 表达绝对时刻，前端再转成本地时区显示。不要把“中国时间字符串”与 UTC 时间戳混着存，尤其在跨时区部署时。

### 10.4 OSIV、懒加载和 N+1

配置 open-in-view=false，避免让数据库会话一直延伸到响应序列化阶段。若未来加实体关联，Controller 访问懒加载字段可能失败，应该在 Service 明确查询和映射 DTO，而不是重新打开 OSIV 掩盖问题。

N+1 指先查 N 条主记录，再为每条记录单独查关联数据。可用批量查询、投影、适当 fetch join 处理，但不要一股脑把所有关联改 EAGER，否则可能产生巨大结果集。

### 10.5 Hikari 连接池

数据库连接创建成本高，连接池复用连接。连接池大小不是越大越好：MySQL CPU、I/O 和锁竞争都有上限。20 个连接只是教学默认值，应结合数据库容量和接口耗时测量。

连接池超时可能是连接泄漏，也可能是慢事务或锁等待。先检查活跃数、等待数、慢 SQL、事务时长，再决定是否扩大池。

## 11. 数据模型、约束与 Flyway

### 11.1 七张核心表

| 表 | 负责什么 | 重要约束 |
|---|---|---|
| app_user | 身份和角色 | username 唯一 |
| shelter | 共享站和容量 | 主键、辖区索引 |
| supply_lot | 每个库存批次 | 站点外键、版本字段 |
| relief_request | 求助单 | request_no 唯一、用户外键 |
| allocation | 请求到库存批次的分配明细 | request_id + supply_lot_id 唯一 |
| outbox_event | 待发布业务事件 | 发布状态和下次重试时间 |
| audit_log | 操作记录 | 操作者和时间索引 |

V2 新增 requester_id + idempotency_key 唯一约束。历史记录的 key 为 NULL，因此无需伪造旧请求幂等键。新接口必须提供有效 key。新索引支持按居民和创建时间检索。

### 11.2 规范化和冗余

把库存批次单独建表，是因为同类物资有不同有效期和剩余量。把 allocation 单独建表，是因为一张请求可能消耗多个批次，一个批次也可能服务多个请求。

不是越多表越好。若为了查询方便加入冗余数量字段，要设计谁负责更新、如何校验和修复。当前 available = quantity - reservedQuantity，不维护第三份数字，减少一致性负担。

### 11.3 约束比“先查一下”更坚固

两个并发事务都可能先查“没有重复”，然后同时插入。唯一约束是数据库最后一道防线。应用检查负责给友好错误，数据库约束负责避免竞态穿透。

业务还可以增加 CHECK(quantity >= 0)、CHECK(reserved_quantity <= quantity) 等约束；当前并未全部增加，不能声称数据库已覆盖所有数值不变量。

### 11.4 Flyway 工作方式

V1 是已经执行的历史迁移，新增结构写 V2，后续继续 V3。不要修改线上已经执行的 V1 来“补字段”，否则校验和变化可能导致启动失败。

JPA ddl-auto=validate 只检查映射，不代替迁移。修改 Java Entity 后必须考虑数据库升级路径、旧数据、默认值和回滚方案。MySQL DDL 往往不能像普通业务 DML 一样整段回滚，部署前应在副本或测试库验证。

## 12. 索引、执行计划与分页的代价

### 12.1 B+Tree 与回表

InnoDB 聚簇索引的叶子保存行数据；二级索引叶子带主键，查询可能先通过二级索引找到主键，再回聚簇索引读取其他列，这就是常说的回表。

覆盖索引指所需列都在该索引内，可以减少回表。索引不是缓存完整查询结果。每增加一个索引，插入更新维护成本和空间成本也会增加。

### 12.2 联合索引要贴着查询设计

居民列表常见条件是 requester_id = ?，按 created_at、id 排序，因此 V2 加入 (requester_id, created_at, id)。如果再加 status 过滤，最佳索引可能随数据分布变化，不能只凭“有状态字段”就判断高效。

现有 (status, priority, created_at) 并不等同于“任何按时间排序都高效”。priority 是字符串枚举，字典序也不等同于业务紧急顺序，若未来按紧急程度自动调度，应显式定义排序权重。

### 12.3 EXPLAIN 的阅读顺序

先看访问表顺序与 rows 估计，再看 possible_keys、key、过滤比例、是否 Using filesort/temporary。EXPLAIN ANALYZE 会实际执行查询并给出运行信息，不能把会修改数据的语句当作无害观测。

不要仅凭 type=ALL 判定坏查询：小表全扫可能很合理；也不要仅凭用了索引就判定快：低选择性范围可能仍扫描大量数据。

### 12.4 LIKE 与深分页

keyword 采用包含匹配 %keyword%，一般不能像前缀查询那样直接定位 B+Tree 范围。用户数据大时可考虑精确查编号、前缀查编号，或有明确需求时引入搜索系统。

OFFSET 大时，数据库需要跳过前面的记录。游标分页可使用 (createdAt,id) 作为边界：

~~~sql
SELECT request_no, created_at, id
FROM relief_request
WHERE requester_id = ?
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 20;
~~~

这是演进示例，当前接口仍是 offset 分页。不要在没有几万到几十万级数据测量之前，为了“架构先进”先引入复杂检索系统。

## 13. 事务与隔离级别

### 13.1 ACID 不能只背中文名

Atomicity：失败后恢复到事务前的一致状态。Consistency：由约束与业务规则共同维持有效状态。Isolation：并发事务之间的可见性和干扰规则。Durability：提交结果在既定持久化配置下保留。

事务保证的是其管理资源中的操作。MySQL 事务不会自动回滚已经发出的 HTTP 请求或 Redis 写入，也不会自动撤回 RabbitMQ 消息。

### 13.2 脏读、不可重复读、幻读

脏读是读取未提交数据。不可重复读是同事务重复读同一行看到不同已提交值。幻读是相同条件出现集合变化。解释时必须说明快照读还是锁定读、隔离级别和 SQL 条件，不要只说“MySQL 默认级别解决全部幻读”。

InnoDB MVCC 借助历史版本提供一致性读。普通 SELECT 与 FOR UPDATE 的语义不同；分配库存需要锁定读看到可更新的行，并保持写锁直到事务结束。[MySQL 8.4 锁定读文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

### 13.3 本项目的事务边界

AllocationService.allocate 使用 READ_COMMITTED 和 5 秒事务超时。先锁求助行，再查并锁库存批次，写分配明细，更新状态，插入 Outbox，最后提交。

全局数据库默认仍可能是 REPEATABLE_READ。方法级隔离是特定业务边界的选择，不能拿连接启动日志中的默认级别否定该方法的配置。

事务超时也不等价于所有网络 I/O 的严格墙钟截止时间。连接获取、数据库锁等待、语句执行各有自己的超时设置，应分别测试。

### 13.4 回滚和异常捕获的位置

唯一键冲突使当前事务失败后，不应在同一事务中假装恢复再继续读写。Controller 捕获 service 事务抛出的 DataIntegrityViolationException 后，重新调用只读 replay 方法，使用新的事务读取旧结果。

这也是为什么“所有代码都放一个 @Transactional 方法”不总是正确。事务边界是业务设计的一部分。

### 13.5 死锁与重试

两笔事务以相反顺序锁资源，可能形成环形等待。当前固定按请求行再按有效期和 ID 访问批次，减少死锁机会，但不能宣称消除所有死锁。

失败重试应有次数上限、退避，并且只重试可恢复的技术冲突。库存不足不是死锁，不应盲目重试十次。重复分配也不是网络失败，应返回冲突。

## 14. 库存分配的逐步推演

假设某辖区饮用水存在两个批次：

| 批次 | 总量 | 已预留 | 可用 | 有效期 |
|---|---:|---:|---:|---|
| A | 10 | 4 | 6 | 较早 |
| B | 20 | 2 | 18 | 较晚 |

请求需要 15 份。分配从 A 取 6，再从 B 取 9。最终 A 已预留 10，B 已预留 11，创建两条 allocation，求助状态 ALLOCATED。

### 14.1 FEFO 与 FIFO 不同

FEFO 按过期时间优先，FIFO 按入库时间优先。无有效期批次不能被 MySQL 的 NULL 升序规则排到最前面，所以查询明确把 expiresAt 为 null 的批次放最后，再按有效期、ID 排序。

### 14.2 为什么先锁求助行

若两个管理员同时分配同一单，只锁库存可能使它们都在一开始读到 PENDING。现在先锁唯一请求行，第二个事务必须等待；第一个提交后，第二个看到已分配状态，返回 409。

这保护的是同一请求重复分配。不同请求竞争同一批次，仍靠库存批次锁、可用量计算和同事务更新保护。

### 14.3 部分分配

有库存但不足时，事务记录已有分配，状态 PARTIALLY_ALLOCATED；完全没有可用库存时返回冲突，不写分配成功状态。

当前 allocate 接口只接受 PENDING，**不支持部分分配后再次补分配**。领域方法允许的状态比服务入口更宽，并不代表 API 已实现完整补单逻辑。正确补分配要减去历史已分配量，考虑同请求同批次唯一约束，并设计通知语义。

### 14.4 不要过度解释 unique allocation

(request_id, supply_lot_id) 唯一约束防止同请求同批次产生两条重复明细，但它不等同于防超卖。防超卖依赖所有写入路径遵守锁和事务规则。如果另一段 SQL 无条件修改 reserved_quantity，仍可能破坏不变量。

## 15. 幂等：重试不会变成重复业务

### 15.1 三类“重复”

双击按钮；网络超时后重试；反向代理或客户端自动重放。前端 disable 只能减少第一类，不能解决后两类。用户也可能打开两个标签页。

前端为一次相同提交保留 UUID 幂等键；失败后重试复用同一键，成功后才清除。如果用户改变内容，生成新键，代表新的业务请求。

### 15.2 当前实现的两层设计

MySQL 是长期事实来源：同 requesterId + idempotencyKey 唯一，保存请求正文对应的业务字段。Redis 是短期协调层：减少同一键的并发重复处理。

实际流程：

1. 校验幂等键长度。
2. 按当前用户和键查数据库。
3. 找到且正文一致，直接返回同一 requestNo 和当前状态。
4. 找到但正文不同，返回 409。
5. 没找到，SET NX 获取两分钟租约。
6. 事务创建记录，数据库唯一约束兜底。
7. Redis 保存 DONE 标记，保留 24 小时。
8. 失败时按租约持有者值执行 Lua 删除。

即使 Redis 标记过期，数据库中仍有键，重试仍可回放。不要把“Redis 24 小时 TTL”误解成业务允许 24 小时后重复创建。

### 15.3 随机值与 Lua 为什么必要

A 获得锁后暂停，锁超时；B 获得新锁；A 恢复后执行 DEL，会误删 B 的锁。释放时必须比较当前 value 是否还是 A 的随机 owner。

比较和删除需要是一个原子步骤，否则在 GET 与 DEL 之间仍可能发生替换。Lua 提供这类原子脚本执行能力。这里借鉴的是 Redis 单实例租约模式，不宣称实现跨机房共识锁。[Redis 官方锁模式](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 15.4 失败窗口逐个分析

| 失败位置 | 数据库可能如何 | 客户端下一步 |
|---|---|---|
| 获取租约之前 | 无新记录 | 同键重试 |
| 事务提交之前 | 回滚或尚未写入 | 同键重试，可能暂时 409 |
| 事务已提交、Redis 标记失败 | 记录已存在 | 同键重试，从 DB 回放 |
| 返回响应途中断线 | 记录已存在 | 同键重试得到原编号 |
| 同键但正文改变 | 原记录保留 | 409，用户确认是否新请求 |

当前 Redis 故障时新建请求不会自动绕过租约走纯 DB 逻辑；会失败并提示重试。已存在记录的 DB 回放在访问 Redis 前完成。这个可用性选择应写清楚，不能同时声称“Redis 必须成功”和“Redis 坏了全部写接口仍可用”。

## 16. Redis：缓存、限流、租约是不同问题

### 16.1 Cache Aside

查站点：先 Redis，命中解码；未命中查 MySQL，再回填。数据库是事实源。Redis 异常时查询退回数据库。空列表也缓存，避免反复查询不存在的辖区。

当前正常和空结果都使用约 270～330 秒 TTL，代码注释里的“短暂”不应理解为空结果拥有独立更短 TTL。若恶意枚举大量不存在辖区，应增加辖区白名单或限制，不能只靠空值缓存。

### 16.2 穿透、击穿、雪崩

穿透：请求的数据根本不存在，持续绕过缓存。空值缓存或过滤器可缓解。

击穿：单个热点 key 过期，大量请求同时回源。互斥重建、逻辑过期和后台刷新可缓解，当前没有完整热点重建互斥。

雪崩：大量 key 同时过期或缓存集群整体不可用。TTL 抖动只缓解“同时过期”，不能解决 Redis 整体宕机后的数据库洪峰，还需要限流、降级和容量设计。

### 16.3 缓存一致性

当前共享站没有写接口，因此没有完整的更新失效链路。未来加入编辑站点，应在数据库提交之后删缓存；删除失败需要重试或变更事件补偿。

“先删缓存再写数据库”可能让其他请求在写入前读到旧值并回填。延迟双删也不是数学意义的绝对一致，仍要明确可接受陈旧窗口和补偿机制。

### 16.4 固定窗口限流

当前按 IP 和分钟分桶，每分钟 120 次。Lua 将 INCR 与首次 EXPIRE 放在一起，避免计数后进程退出导致没有 TTL。超额返回 429 与 Retry-After。

窗口边界可能瞬间通过两倍流量。例如前一分钟末尾 120 次，下一分钟开头 120 次。需要更平滑行为时可用滑动窗口或令牌桶。当前全 API 共用 IP 配额，多人共用 NAT 会相互影响，登录接口也没有独立更严格策略。

### 16.5 Redis 数据结构如何选

String 可存 token、序列化对象、计数器；Hash 适合部分字段操作；Set 用于去重成员；Sorted Set 适合带时间分数的窗口；List 可做简单队列；Stream 提供消费组等消息能力。项目实际主要使用 String 和 Lua，不因为知道这些名词就引入所有结构。

持久化 AOF 与 RDB、淘汰策略、内存限制、热 key、大 key 都需要运维设计。Compose 中启用 Redis AOF 不等于已经配置稳定的数据卷和高可用集群。

## 17. RabbitMQ 与 Outbox

### 17.1 为什么不能事务里直接发送就算完成

数据库提交和 MQ 接收是两个独立系统中的事件。先发消息再提交数据库，可能消费者已经收到但数据库回滚；先提交数据库再发消息，可能进程在两步之间崩溃。

Outbox 把“需要发送的事件”作为数据库行，与业务修改同事务保存。这样业务提交后一定有可重试的事件记录。

### 17.2 本项目的发布链路

定时任务每次最多读取 50 条到期的 PENDING 事件，并加数据库写锁。RabbitTemplate 发布到 resilience.events，路由键 allocation.created。队列 allocation.notification 绑定 allocation.#。

现在发布器等待 CorrelationData Future，最多等待 5 秒，检查 broker ack 和 returned 消息。确认且可路由才标记 PUBLISHED；异常则增加重试次数、更新下次时间，达到 10 次进入 FAILED。[Spring AMQP 发布确认说明](https://docs.spring.io/spring-amqp/reference/amqp/template.html)

### 17.3 三种“成功”不能混用

发送 API 没有立即抛错；broker 接收确认；消费者完成业务。这三者分别处于不同阶段。Publisher Confirm 不证明消费者完成通知，Consumer Ack 不证明上游数据库的某个事务刚刚提交。

本项目通过 confirm 加 returns 检查发布侧，不提供“短信已送达”的证明。消费者只是日志模拟。[RabbitMQ 官方确认说明](https://www.rabbitmq.com/docs/confirms)

### 17.4 为什么仍会重复

broker 已确认，应用还没更新 PUBLISHED 就崩溃，Outbox 保持待发布，重启后会再次发送。消息 ID 使用 Outbox ID，便于消费端识别重复。业务语义因此是可重复投递，需要幂等消费。

NotificationConsumer 使用 Redis 去重标记后写日志。这只是演示：如果换成真实短信，在写去重标记后、调用供应商前崩溃，会跳过未发送的通知。生产上需要通知任务表、状态机、供应商幂等键或可靠补偿，不能把当前消费者称为 exactly-once。

### 17.5 当前 Outbox 的吞吐限制

发布确认等待发生在持锁事务里，50 条消息在异常情况下可能放大持锁时间。多实例会有锁竞争，尚未实现 SKIP LOCKED 任务认领或租约分段发布。

这是一种可理解、可演示的实现，但不是大吞吐标准答案。改造时可把“短事务认领 → 事务外发送 → 短事务确认结果”拆开，并处理认领过期、重复投递和故障恢复。

## 18. 安全：身份、操作权限、对象权限

### 18.1 三个层次

认证：你是谁？JWT 验证后得到 username 和 role。

操作权限：这个角色能否调用分配接口？@PreAuthorize 要求 ADMIN。

对象权限：居民能否读这个 requestNo？Service 比较 requesterId 与登录用户 ID。只是“登录了”不代表能看所有对象。

本轮增加对象级授权，查询别人的请求与查询不存在请求都返回 404，减少编号枚举的信息差。

### 18.2 JWT 不是加密

JWT 的 header 和 payload 使用 Base64URL 编码，可直接解码。HS256 是签名校验，不提供内容保密。不要把密码、身份证、手机号等敏感内容塞进 Token。

项目验证固定 header、HMAC 签名和 exp；签名比较使用常量时间比较方法。当前是教学实现，payload 解析较严格，尚未提供 issuer、audience、密钥轮换、撤销、刷新令牌完整机制。

### 18.3 Token 存储与 XSS

前端 Token 存 localStorage，页面中的脚本可以访问它，因此防 XSS 很重要。动态内容通过 escapeHtml 转义，避免把接口字段作为 HTML 执行。

HttpOnly Cookie 可降低脚本直接读取 Token 的风险，但会引入 Cookie 自动携带时的 CSRF 设计问题。不能把“换成 Cookie”当作一键安全。当前 Bearer 方案禁用 CSRF，是基于不依赖浏览器自动附带认证 Cookie 的架构。

### 18.4 密码与演示账号

V1 中演示账号实际上是 {noop} 密码，旧 SQL 注释提到 BCrypt 并不准确。运行配置使用 DelegatingPasswordEncoder，可以支持不同编码格式，但数据库里的数据不会自动被它改成 BCrypt。

生产前必须迁移演示密码、移除默认账号、设置独立 JWT_SECRET、限制服务暴露、启用 HTTPS。当前没有 MFA、登录锁定、账户禁用后即时 Token 失效等完整账号治理。

### 18.5 SQL 注入、越权、信息泄露

参数化查询解决拼接 SQL 导致的注入；授权条件解决访问别人数据；响应 DTO 解决不该公开字段；统一错误解决内部堆栈泄露。它们各自针对不同攻击面，没有一个注解可以替代全部。

## 19. 网络、操作系统与部署

### 19.1 HTTP 与 TCP

HTTP 描述请求与响应，TCP 提供可靠字节流。TCP 重传不等于 HTTP 业务不会重复：连接在响应阶段断开后，客户端重试仍可能产生第二次业务请求，所以业务幂等不能由 TCP 代替。

连接超时与读取超时不同：前者可能是无法建立连接，后者可能是服务端已开始处理但迟迟不返回。超时代表客户端不知道结果，不代表业务一定没发生。

### 19.2 DNS、TLS、反向代理

浏览器解析域名，再建立连接，HTTPS 还要完成 TLS 握手。反向代理可以终止 TLS、转发请求、限制请求体、提供负载均衡，但也会引入超时与转发头的信任边界。

当前限流使用 remoteAddr，不盲信客户端提供的 X-Forwarded-For。上线经过代理后，需要只信任已配置代理节点，并正确恢复真实客户端身份，否则所有用户可能共用代理 IP 配额。

### 19.3 进程、线程、文件描述符

Java 进程包含多个线程和内存区域。数据库连接、socket、日志文件都消耗系统资源。端口冲突不是 Spring 的业务错误；文件描述符耗尽也不会靠增大 JVM 堆解决。

容器不是虚拟机的完整替代品，它共享宿主内核。Docker Compose 的 localhost：应用跑在宿主时指宿主；应用跑进容器时指应用容器本身，应改 DB_URL 使用 mysql 服务名。

### 19.4 Docker 与发布流程

当前 Dockerfile 将 JAR 复制进 Java 21 JRE 镜像，以非 root UID 运行。Compose 主要提供三个依赖，不包含完整应用集群部署。

发布步骤应该包含：构建测试、数据库迁移验证、配置检查、启动健康检查、流量切换、观察指标。不要先开放公网再修改默认密码。也不要为修复迁移失败随意删除 Flyway 历史表或业务卷。

## 20. 可观测性、测试和性能

### 20.1 日志、指标、链路各回答什么

日志回答“一次失败发生了什么”；指标回答“总体在什么时候变坏、程度如何”；链路回答“一次请求时间花在哪个服务”。

Actuator health 是依赖可用性信号，不证明每条业务路径都正确。Prometheus 端点暴露指标，也不代表已经部署采集器、仪表盘和告警。

### 20.2 单元测试与集成测试

Mockito 测试能验证 Service 的分支、授权、状态判断和调用契约，但无法证明 MySQL 实际加锁行为。真实服务 smoke 用本地 MySQL、Redis、RabbitMQ 验证接口和并发分配；它会新增少量演示数据。

Testcontainers 依赖已经存在，但项目尚没有完整的自动容器化集成测试套件。不能用“pom 有依赖”替代实际测试代码和运行证据。

### 20.3 不只测试成功

需要测试：同键同正文、同键不同正文、未登录、居民调用管理员接口、居民查他人详情、非法枚举、负页码、库存不足、重复分配、并发分配、刷新响应乱序、分页失败。

每个测试应对应一个可观察业务断言。只验证“方法被调用一次”不等于库存正确，Mockito 与真实数据库测试要互补。

### 20.4 性能分析方法

先定目标：吞吐量、P95/P99 响应时间、错误率、数据量和并发模型。再测基线，再改变一个变量。只拿平均响应时间会掩盖长尾；只看 QPS 不看错误率可能是在快速失败。

容量模型的一种粗略估计：并发中的请求数约等于吞吐量乘平均耗时。它可以帮助解释连接池排队，但不能代替真实负载测试，尤其在热点锁、重试风暴和长尾等待场景中。

### 20.5 常见优化顺序

先消除 N+1 与无界列表；检查索引和慢 SQL；缩短事务持锁时间；处理缓存命中和热点；限制并发与重试；最后才考虑拆服务、分库分表。每一步都需要测量前后变化。

## 21. 前后端协作不是“把接口调通”

当前界面采用普通工作台、列表、详情、表单，删除虚构地图和统计图。服务器是记录来源：重新登录或换设备后，居民列表可按自己的身份查询。

### 21.1 竞争响应

用户先输入 A，再输入 B，B 的响应先回来，A 后回来。前端不能让 A 覆盖 B。现在查询带递增版本号，只有最新版本的响应更新页面。

搜索有 350ms 防抖，减少每个按键都请求服务器。防抖不是幂等，也不代替后端限流。

### 21.2 请求成功与页面成功

HTTP 写入成功后，刷新列表可能失败。用户必须能看到创建成功的编号，而不是因为列表刷新失败就以为创建失败。提交和刷新是两个阶段，应分别处理。

401 会清理登录态，403 保留登录并显示无权限。早先把 403 当作 Token 过期，会让居民误调用管理员操作时被退出，这属于协议理解错误。

### 21.3 当前前端边界

管理员能看到全平台记录，居民只能看到自己的记录。详情使用服务器最新数据。新建失败后保持相同内容的幂等键，帮助处理响应丢失后重试。

尚未支持取消、部分补分配、通知收件箱、库存管理和导出。不要让没有后端语义的按钮看起来可用。

## 22. 学习计划与完成标准

### 22.1 四周路线

| 周 | 主题 | 产出 |
|---|---|---|
| 第 1 周 | Java、HTTP、MVC、身份 | 手画请求链路，独立调用登录、创建、查询 |
| 第 2 周 | SQL、索引、事务、JPA | 两连接锁实验、EXPLAIN 分析、越权测试 |
| 第 3 周 | Redis、幂等、MQ | 幂等故障时序图、Outbox 重投递实验 |
| 第 4 周 | 并发、JVM、测试、部署 | 自动回归脚本、性能基线、项目讲解录音 |

### 22.2 读懂一个模块的标准

能不看代码解释输入、输出、不变量、失败路径；能找到控制它的配置；能写一个成功测试和两个失败测试；能说出一个当前限制；能提出一个有成本说明的演进方案。

### 22.3 下一阶段值得做的真实改造

1. 部分分配补单：先定义历史已分配量、重复批次明细和通知规则。
2. 真实通知任务：建立可重试状态机、供应商幂等键、失败追踪。
3. 用户体系：BCrypt 数据迁移、刷新/撤销、密钥轮换与审计。
4. Outbox 认领：减少发送时长事务，支持租约超时恢复和 SKIP LOCKED。
5. 测试隔离：用 Testcontainers 构建可重复的 CI 集成测试。
6. 库存管理：入库、过期处理、取消释放、签收，与现有预留量一起维护不变量。
7. 查询扩展：游标分页、明确的跨字段搜索，而不是让所有 LIKE 都走全表。
8. 运维：消息与缓存数据卷、TLS、监控告警、备份恢复演练。

学习文档中的理论范围比已实现功能广。掌握知识的标准不是给项目贴更多中间件标签，而是能用实验说明当前实现为什么有效、在哪些情况下需要改变。
